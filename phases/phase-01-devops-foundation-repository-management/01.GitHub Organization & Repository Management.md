```text

```

This gives us:

```text

       v

Platform/DevOps team
       |
       +------> infrastructure
       |
       +------> gitops
       |
       +------> platform
```

This is much closer to how larger organizations operate.

# 13. Branching Strategy

We will use:

```text
main
```

as the protected production-ready branch.

Developers don't directly work on `main`.

Example:

```text
main
 |
 +---- feature/order-validation
 |
 +---- feature/payment-integration
 |
 +---- bugfix/order-timeout
 |
 +---- hotfix/order-api
```

Developer creates:

```bash
git checkout main

git pull origin main

git checkout -b feature/order-validation
```

Work happens on:

```text
feature/order-validation
```

Then:

```bash
git add .
git commit -m "feat: add order validation"

git push origin feature/order-validation
```

Then create Pull Request:

```text
feature/order-validation
             |
             v
           main
```

# 14. Commit Convention

Use meaningful commits.

Good:


```text
changes
update
test
final
final2
working
new changes
```

This becomes very useful when troubleshooting production releases.

# 17. Why CODEOWNERS Matters

Imagine a developer submits:

```text
PR #125

Change production CPU limits
```

They modify:

```yaml
resources:
  limits:
    cpu: 8
```

Without ownership:

```text
developer
    |
    v
merge
    |
    v
production
```

Potentially dangerous.

With CODEOWNERS:

```text
developer
    |
    v
PR
    |
    v
platform-team review
    |
    v
approval
    |
    v
merge
```

This gives us a governance layer.

# 19. First CI Pipeline

Now we create:

```text
.github/workflows/ci.yaml
```

Initial version:

```yaml
name: Order Service CI

on:
  pull_request:
    branches:
      - main

  push:
    branches:
      - main

permissions:
  contents: read

jobs:

  build:
    name: Build and Test
    runs-on: ubuntu-latest

    steps:

      - name: Checkout source code
        uses: actions/checkout@v4

      - name: Setup Java
        uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '21'
          cache: maven

      - name: Build application
        run: ./mvnw clean package

      - name: Run tests
        run: ./mvnw test
```

This is our **starting CI**.

# 20. Very Important: CI vs CD

This distinction should be clear from day one.

### CI

Application repository:

```text
GitHub
   |
   v
Source Code
   |
   v
Build
   |
   v
Test
   |
   v
Scan
   |
   v
Docker Image
   |
   v
Amazon ECR
```

### CD

Then:

```text
ECR
 |
 | image: 1.5.2
 v
GitOps Repository
 |
 v
ArgoCD
 |
 v
EKS
 |
 v
Kubernetes Pods
```

So:

```text
Application Repo
       |
       | CI
       v
      ECR
       |
       v
    GitOps Repo
       |
       | CD
       v
     ArgoCD
       |
       v
      EKS
```

This separation is one of the most important concepts in our project.

# 21. We Will NOT Do This

Avoid this production pattern:

```text
GitHub Actions
      |
      v
kubectl apply
      |
      v
Production EKS
```

Instead:

```text
GitHub Actions
      |
      v
ECR
      |
      v
GitOps PR
      |
      v
Approval
      |
      v
ArgoCD
      |
      v
Production EKS
```

This gives us:

* auditability
* Git-based history
* controlled promotion
* rollback
* separation of CI/CD permissions
* easier compliance

# 23. Environment Promotion

Our eventual lifecycle:

```text
Developer
    |
    v
Pull Request
    |
    v
main
    |
    v
Build Image
    |
    v
ECR
    |
    v
DEV
    |
    v
QA
    |
    v
STAGING
    |
    v
PRODUCTION
```

Example image:

```text
order-service:8f72a91
```

The same immutable image should move through environments.

We don't want:

```text
DEV -> build image A

QA -> build image B

PROD -> build image C
```

because then we're not testing exactly what we're deploying.

Prefer:

```text
Build once

order-service:8f72a91
       |
       +--> DEV
       |
       +--> QA
       |
       +--> PROD
```

This is a major production CI/CD principle.
